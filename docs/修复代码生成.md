# 修复代码生成

## 修复范围

本次修复了 CRUD 代码生成器处理前端目录时的路径规范化问题。该问题会影响两类生成结果：

- 菜单 SQL 的页面组件路径。
- Vue 页面中导入 API 模块的别名路径。

当前修复位于 `server/internal/library/hggen/views/curd.go` 的 `webModulePath` 函数。后续使用代码生成器新增模块会应用该逻辑。

## 问题一：菜单页面显示为空白

错误的菜单组件路径包含 `views` 目录：

```text
/views/forum/topic/index
```

前端动态路由以 `web/src/views` 为组件根目录，因此正确值必须是：

```text
/forum/topic/index
```

错误值无法匹配实际文件 `web/src/views/forum/topic/index.vue`，因此访问 `/#/forum/topic/index` 时页面为空白。

### 原因与修复

生成器此前仅移除了 `../web/src/` 前缀，保留了 `views`，导致菜单 SQL 中的 `component` 字段错误。现在生成器会按 `web/src/views` 截取相对目录，兼容以下配置格式：

```text
../web/src/views/forum
web/src/views/forum
P:/go/hotgo-2.0/web/src/views/forum
/opt/hotgo/web/src/views/forum
```

生成的菜单组件路径为：

```text
/forum/topic/index
```

主题和举报模块的已生成菜单 SQL 已同步为正确格式：

```text
server/storage/data/generate/topic_menu.sql
server/storage/data/generate/report_menu.sql
```

已入库的旧菜单可分别执行以下一次性修复程序：

```powershell
cd P:\go\hotgo-2.0\server
go run hack/exec_fix_forum_topic_menu.go
go run hack/exec_fix_forum_report_menu.go
```

程序分别将 `topicIndex` 和 `reportIndex` 菜单的 `component` 字段更新为 `/forum/topic/index` 和 `/forum/report/index`。

## 问题二：Vue 页面无法解析 API 导入

生成的评论模块曾包含错误导入：

```ts
import { List, Export, Delete } from '@/../web/src/api/forum/comment';
```

`@` 指向 `web/src`，不能再拼接 `../web/src`。Vite 因此报错：

```text
Failed to resolve import "@/../web/src/api/forum/comment"
```

### 原因与修复

API 路径使用了与菜单组件路径相同的旧前缀处理方式。现在生成器按 `web/src/api` 截取相对模块目录，生成：

```ts
import { List, Export, Delete } from '@/api/forum/comment';
```

当前评论模块的 `index.vue`、`edit.vue`、`view.vue` 已全部使用正确导入。全项目扫描未发现 `@/../web/src`、`../web/src/api` 或 `../web/src/views` 的残留引用。

### 补充：IM 模板遗漏 `api/` 前缀

会话模块配置的 API 生成目录为 `../web/src/api/im`。路径规范化后得到的相对目录为 `im/conversation`，但生成器此前仅拼接 `@/`，错误生成：

```ts
import { List, Export, Delete } from '@/im/conversation';
```

实际文件位于 `web/src/api/im/conversation/index.ts`，因此正确导入必须是：

```ts
import { List, Export, Delete } from '@/api/im/conversation';
```

生成器现在固定以 `@/api/` 作为 API 导入别名前缀，适用于 `im`、`forum`、`web`、`openai` 等所有非插件 CRUD 模板。会话模块的 `index.vue`、`edit.vue`、`view.vue` 已同步修正。

## 问题三：`/admin/report/list?page=1&pageSize=10` 请求报错

举报模块生成的接口契约为 `/report/list`。后台路由组会自动加上 `/admin` 前缀，因此浏览器请求：

```text
/admin/report/list?page=1&pageSize=10
```

是正确的生成结果，不是前端 API 路径生成错误。

代码生成后，后端必须重启，新增的 `api`、`controller` 和 `internal/router/genrouter` 路由才会注册。若未重启，接口会返回 404；重启后若请求没有有效登录信息，会进入鉴权并返回登录身份失效提示，说明路由已经生效。

## 问题四：同一模块生成相似实体时 service 接口重复

论坛模板中先后生成了实体 `Category` 和 `ForumCategory`。旧规则会省略模块前缀或以不一致的方式拼接服务名，导致两份逻辑最终都映射到 `ForumCategory`。GoFrame service 生成器将它们合并到同一个接口后，接口中出现重复的 `Model`、`List`、`Export`、`Edit` 等方法，后端无法编译。

### 原因与修复

代码生成器现在始终采用“模板模块前缀 + 实体名”的服务标识：

```text
forum + Category      -> ForumCategory
forum + ForumCategory -> ForumForumCategory
```

因此同一个模板下的实体即使名称相似，也会生成独立的逻辑结构体、注册函数和 service 接口。现有论坛代码已同步为以下两个服务：

```text
service.ForumCategory()
service.ForumForumCategory()
```

`server/internal/library/hggen/internal/cmd/genservice` 还增加了接口方法重名预校验。若未来已有人工代码或异常生成结果使同一服务接口出现重复方法，生成会返回明确错误，不再写出无法编译的 service 文件。

## 问题五：构建失败仍被标记成功

此前提交生成时，记录会在实际生成之前更新为成功。SQL 菜单导入失败后仅删除 SQL 文件而不返回错误，因此页面可能显示生成成功，但生成的后端路由、菜单和 service 实际不完整。

### 原因与修复

现在构建顺序为：

1. 保存生成配置。
2. 生成并导入 SQL、写入代码、生成 DAO 和 service。
3. 任一步失败立即返回错误，并将记录标记为失败。
4. 全部步骤完成后，才将记录标记为成功。

SQL 导入失败会返回“导入生成菜单 SQL 失败”及对应文件路径，不再被吞掉。service 文件写入也改为同步执行，文件系统错误会传递给构建接口。

## 问题六：模板配置与插件路径状态串用

插件模板路径含 `{$name}` 占位符。旧实现会直接修改共享的生成配置对象；同一服务进程后续生成另一个插件或重试时可能继续使用上一插件已替换的路径。

现在每次生成都会复制当前模板配置，在副本中解析插件路径，避免跨请求污染全局配置。

## 问题七：菜单在后续代码生成失败时已提前入库

旧的构建顺序会先写入并执行菜单 SQL，之后才写入其余生成文件和刷新 service。若后续步骤失败，菜单仍会留在数据库中；下一次重试又会因菜单别名已存在而失败，形成“代码未生成完整但无法重试”的状态。

现在构建顺序调整为：

1. 生成 DAO。
2. 写入 API、输入模型、控制器、逻辑、路由及前端文件。
3. 生成 service。
4. 最后写入菜单 SQL 并导入菜单。

因此任一代码生成步骤失败时，不会再新增已入库菜单。菜单 SQL 导入会在单个数据库事务内执行，任一语句失败将整体回滚；生成状态仍会标记为失败，并移除刚写出的 SQL 文件。

## 问题八：并发生成可能互相覆盖

DAO、service 和目标文件目录属于整个项目共享资源。此前后台同时提交两个生成请求时，两个请求可以并行写入同一批文件，导致 service 文件或 DAO 文件被相互覆盖。

现在生成器在进程内串行执行 CRUD 和树表构建请求。单个请求完成前，后续请求会等待，从而避免并发写入共享生成目录。

## 问题九：Windows 删除生成代码后主模块 service 文件被误删

后端启动曾报错：

```text
package hotgo/internal/service is not in std
```

直接原因是 `server/internal/service` 下的 Go 接口文件全部缺失，只剩占位文件。`server/go.mod` 中的模块名以及插件对 `hotgo/internal/service` 的导入路径均正确，无需修改导入或 Go 环境变量。

### 原因与修复

当前 Git 提交已记录删除原有 17 个 service 文件。进一步在临时项目中复现发现，“删除生成代码”会启用 service 清理，而清理实现使用目标目录字符串截取扫描出的绝对路径：

- 配置目录为 `internal/service`，但 Windows 扫描路径为 `P:\go\hotgo-2.0\server\internal\service\sys.go`。
- 两种目录分隔符不一致，截取结果为空，无法匹配本次生成文件集合。
- 文件标记检查将不存在的空路径视为可生成文件，因此会删除有效 service，甚至删除同目录中的手工维护文件。

这解释了该操作如何导致文件全部缺失；Git 删除记录本身不包含当时实际执行操作的证据。

现已在 `internal/logic/sys/gen_codes.go` 的 `refreshBuildServices` 中，将 service 输出目录统一为使用系统分隔符的绝对路径，再调用原有生成器。该修复覆盖主模块与插件的“删除生成代码”流程，不修改基础库或模板。手工文件继续通过原有生成标记规则保护，只有对应逻辑目录已失效的生成接口文件会被清理。

缺失接口已按当前 logic 重新生成，而非直接恢复旧版本接口，以适配当前 `app`、`user` 等模块。需要单独恢复时，在 `server` 目录执行以下命令，保留默认关闭的清理选项：

```powershell
gf gen service -s internal/logic -d internal/service -f Snake
```

新增的临时项目回归测试覆盖主模块和插件：保留有效生成服务，保留手工文件，清理过期生成文件，并确认其他模块不受影响。删除一个逻辑包中的最后一个 Go 文件后，再次刷新也会移除对应的过期 service 文件。

## 问题十：已有代码却显示“未生成”或“生成失败”

### 已确认的原因

- 保存配置原先将完整实体写回数据库，旧页面携带的 `status` 会覆盖后台刚保存的生成结果。回归测试已复现将成功状态覆盖为未生成的情况。
- 实际生成日志记录了 AppDaoban 在写入 `addons/appAuth/service/sys.go` 时遇到 Windows 文件映射占用错误（错误码 1224）。此前步骤写出的文件仍存在，因此“有文件”和“整个生成流程成功”不能等同。
- 历史生成请求耗时约 26～31 秒，前端默认 30 秒超时不足以可靠等待全部请求完成。连接中断也不能直接证明后端生成失败。

只读核对时，AppAuth、AppDaoban、AppLog 都检测到 11 个生成文件，数据库状态分别为成功、失败、未生成。AppLog 当次异常的具体触发原因缺乏完整日志，不能仅凭文件存在认定为生成成功。

### 当前修复

- 配置保存使用更新/新增字段白名单，更新不允许写入状态、主键和时间字段；保存后返回数据库真实状态。
- 生成前记录“生成中”，全部步骤成功才记录成功；失败、异常和最终状态写入失败都会返回错误。客户端断开不会取消最终状态保存。
- 同机进程锁保护共享生成目录，阻止重复提交及生成期间修改配置、删除代码。查询会重新核对状态；查询不再根据锁是否存在将数据库记录改为失败。记录为生成中但未检测到任务时，仅返回“结果待确认”提示，成功或失败终态由生成任务写入。当前仍为同步生成，服务进程被强制结束时不会继续执行任务。
- 服务接口先在临时目录生成、格式化，再通过同目录临时文件替换目标；内容相同则跳过。Windows 短暂占用时重试，持续占用时保留原文件并明确报错。
- 列表同时展示执行状态和实际已有文件数量。未生成但存在文件显示“已有文件，待确认”；失败且存在文件显示“已有文件，未完成”。这些文案由后端返回，不擅自把历史记录提升为成功。
- 生成接口单独使用 10 分钟超时；页面保留后台明确返回的错误，网络中断后核对真实状态，并在返回列表时刷新缓存结果。
- 旧状态为未生成但有文件时也允许通过“删除生成代码”清理，禁止只删配置留下文件；本次修复没有执行该清理，也未修改现有三条生成记录。

历史异常配置可在关闭“强制覆盖”的情况下再次提交生成，默认保留已有代码、补齐缺失步骤。现有菜单及 SQL 已存在时，保持默认跳过，避免重复导入。

## 问题十一：确认框等待生成结束，热重启后详情仍停留在旧结果

### 本次核对结论

- Naive UI 会等待 `onPositiveClick` 返回的 Promise 后再关闭确认框。原回调等待生成及结果核对，所以约 30 秒生成期间确认框一直存在。
- ID 54（AppProducts）首次生成在 2026-10-19 01:30:41 记录生成中，01:31:10 完成生成并保存成功状态；随后日志出现服务重新启动。该次后台记录并非第二次提交才成功。
- `guide-zh-CN/code-help.md` 已说明热编译重启期间接口可能暂时返回服务器错误或 404。原页面成功后只刷新一次详情，刷新失败就停止；状态核对请求还会触发全局网络错误提示。
- 现有日志没有保存用户当时失败的详情响应，不能据此断言“已有文件，未完成”的每一次出现都由相同原因触发，也没有将旧失败记录直接改为成功。

### 修复与验证

- 确认回调同步返回，立即关闭确认框，生成独立执行；生成和状态核对期间保持按钮加载并阻止重复提交。
- 已收到生成成功响应后，详情读取失败会继续核对，服务恢复后自动同步文件和状态。持续无法同步时明确保留“代码已生成”，不将详情同步失败当作生成失败。
- 生成及结果核对显式关闭全局错误提示，由页面展示等待恢复信息。HTTP 封装仅在调用方显式传入 `isShowErrorMessage: false` 时使用静默错误处理，仍拒绝请求；普通请求及业务登录失效提示保持原行为。
- 回归测试执行真实页面脚本及 HTTP 响应处理逻辑，覆盖确认框、重复提交、重启恢复、核对超时、离开页面、明确生成失败、旧成功记录和普通请求提示。

```powershell

node --test src/views/develop/code/deploy.test.cjs src/utils/http/axios/index.test.cjs
```

本次未执行真实代码生成、菜单清理或数据库状态修正。服务热重启期间浏览器网络面板仍可能记录连接失败，页面会继续核对而非要求再次生成。

## 问题十二：新增页面后反复刷新，基本信息一直显示“请稍候”

### 核对结果

- 已阅读 `guide-zh-CN/code-curd.md`、`code-help.md`、`code-config.md` 与 `addon-flow.md`。文档中的插件独立 service、插件路由及前后端输出目录，与当前生成路径一致；热编译重启期间接口短暂失败也在文档中已有说明。
- 路由模块的 `import.meta.glob` 匹配所有视图。真实 Vite 临时项目已复现：新增生成页面时，旧模块图会发送 `full-reload`；逐个生成 index/edit/view 页面便可能导致连续刷新。修复后相同文件新增/删除事件仅发送组件映射的 `js-update`，旧调用方保留的路由函数也能找到新增页面，已删除的页面不会残留。
- `BaseInfo.vue` 原来通过 30ms 定时器等待 ID，然后顺序加载字段、表和菜单；任何一个请求异常都会跳过结束遮罩的语句，而且组件卸载时没有清理等待 ID 的定时器。执行真实组件脚本的回归测试已经复现持续“请稍候”。
- 父配置页原来初始化只请求一次。页面恰好在后端热重启期间重新加载时，选项或详情请求失败，后续基本信息无法正常初始化。
- ID 55 当次日志在 2026-10-19 01:59:15.862 记录生成完成，01:59:15.863 写入成功状态；只读数据库核对却显示 01:59:17 更新为失败。现有日志没有保留下最后一次失败写入，不能断言具体是哪一个请求覆盖。原 `inspectBuild` 的查询分支确实会写失败状态，回归测试已复现这个副作用。

### 修复

- 动态路由增加热更新接收边界，并在热更新数据中保留组件映射对象。新文件仍按 Vite 正常监听，不忽略生成目录、不屏蔽普通页面修改，也不硬编码新菜单路由。生成结束且后端恢复后，可手动刷新一次以重新加载后端菜单。
- 基本信息初始化改为响应 ID/数据库变化，不再使用永久轮询；短暂失败自动重试，持续失败释放遮罩并显示“重新加载”。字段、表、关联表加载标志均在 `finally` 中恢复；离开页面停止重试及后续请求。
- 父配置页加载选项和详情时自动重试，数据加载成功后才挂载子页；持续失败也会结束遮罩并提供重新加载，无需再次提交生成。
- 初始化请求显式传递静默错误选项，避免重启期间反复弹出全局错误；默认普通请求行为保持不变。
- 列表、详情的生成检查保持只读。记录为生成中而当前未检测到任务时，显示“结果待确认”，不推断失败、不改数据库，也不凭文件存在宣称生成成功。

已有失败状态没有直接批量改为成功，已有生成文件及菜单没有执行删除或覆盖。

## 问题十三：生成成功后刷新变成“结果待确认”

### 日志与实际持久状态

ID 56（UserGroup，用户分组）在 2026-10-19 02:57:02.265 写入生成中，02:57:34.885 执行了成功状态更新，菜单导入事务也显示已提交。但 03:03:56 使用独立进程查询时，该记录仍为生成中，更新时间仍是 02:57:02。当前未检测到生成任务时，查询接口会将这类记录显示为“结果待确认”；该查询本身没有修改记录。

因此，这次异常不能仅用前端缓存解释：数据库独立连接也读到了旧状态。日志显示执行过成功 UPDATE，只能证明语句执行成功，不能单独证明事务已提交。

### 已复现的事务机制

生成的 MySQL 菜单脚本含 `SET SQL_MODE`、`SET AUTOCOMMIT = 0`、`START TRANSACTION` 和 `COMMIT`。旧导入器在 GoFrame 事务中逐行执行这些语句，导致两个问题：

- 脚本关闭连接的自动提交后，没有恢复该会话设置，连接返回共享连接池后仍可能处于 `AUTOCOMMIT=0`。
- 脚本自己的 `COMMIT` 会提前提交框架事务内已执行的语句，使之后发生的错误无法整体回滚。

复用这样的连接执行普通状态 UPDATE 时，同一连接可以立即读到成功，其他连接仍读到生成中；连接关闭或事务回滚后，未提交的成功状态丢失。这与 ID 56 的日志及独立查询结果吻合。

实际 MySQL 的会话临时表实验已复现“普通 UPDATE 即时读为成功、丢弃未提交事务后恢复生成中”，并验证显式事务提交后状态可保留。未捕获 ID 56 当时的连接编号及事务现场，因此这里确认的是可复现的代码缺陷及吻合证据，不将历史连接状态描述为现场观测结论，也不据此断言 ID 55 的全部历史异常均由同一原因造成。

### 本次修复

- `internal/logic/sys/gen_codes.go` 的 `Status` 通过 DAO 所属数据库显式开启并提交事务；提交错误会返回，避免仅凭 UPDATE 执行成功就报告生成成功。
- `utility/db/mysql_menu.go` 新增专用于逐行生成菜单脚本的 MySQL 导入函数。事务交由 GoFrame 管理，跳过脚本中的事务控制及 `AUTOCOMMIT`、`SQL_MODE` 会话设置；菜单父 ID、`LAST_INSERT_ID()` 等变量语句保留在同一事务中。
- `internal/logic/sys/gen_codes_build.go` 的 MySQL CRUD/树表流程复用现有预览，按 DAO、代码、service、菜单顺序发布，并调用新的安全导入函数。沿用默认跳过已有文件及强制覆盖的选择；非 MySQL 和非 CRUD/树表流程保持原调用方式。
- 本轮没有修改 `internal/library/`、模板或 CLI 生成的 entity、do、dao/internal 文件。独立执行所用的生成 SQL 文件也不需要改写。

更新代码后需完整停止并重新启动后端，使用新编译结果并释放旧连接池中的会话。仅刷新浏览器不能清除后端连接设置。历史 ID 56 的生成中状态未被自动改为成功；重启也不会恢复已经丢失的未提交状态。应另行核对历史生成结果后再确认状态修正，不能仅凭已有 11 个文件自动提升为成功，也无需为修正文案而删除已有代码或菜单。
